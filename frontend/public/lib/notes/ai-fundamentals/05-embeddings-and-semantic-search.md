# Embedding与语义检索：从文字到向量

Embedding（向量化）是现代 AI 应用里最被低估的基础技术：RAG 的检索靠它、推荐系统靠它、记忆系统也靠它。好消息是，它的核心思想用一个比喻就能讲清楚——**把一段文字变成语义空间里的一个坐标点，意思越接近的点，离得越近**。

## 为什么关键词检索不够用？

传统搜索靠关键词匹配，它有两个天然盲区：

- **同义不同词**：搜"电脑开不了机"，匹配不到"主机无法启动"——没有共同关键词，但显然是同一个问题
- **一词多义**：搜"苹果"，水果官网和手机官网都会命中，关键词分不清语境

语义检索的思路是：**不比较字面，而是比较意思**。要做到这一点，得先把"意思"变成可计算的东西——这就是 Embedding 的任务。

## Embedding 是什么？

把文字交给一个 Embedding 模型，它会输出一串浮点数（比如 1536 个），这就是这段文字的**向量表示**：

```
"如何退货？"           → [0.12, -0.35, 0.87, ..., 0.21]
"退款流程是什么？"     → [0.11, -0.33, 0.85, ..., 0.19]   ← 和上一条非常接近
"今天天气真好"         → [-0.42, 0.76, -0.15, ..., 0.63]  ← 离得很远
```

可以把每个维度想象成语义空间里的一个"特征方向"——有的方向偏向"情感色彩"，有的偏向"主题领域"，有的偏向"正式程度"。单个维度没有人类可读的含义，但 **1536 个维度合起来，就精确地定位了这段文字在语义空间中的位置**。

关键性质只有一个：**语义相近的文本，向量距离就近**。同义改写、跨语言翻译、总结与原文，向量都会聚在一起。

## 怎么衡量"近"？——余弦相似度

比较两个向量常用**余弦相似度**：夹角越小，越相似。

- 完全相同方向 → 相似度 1
- 毫无关联（正交） → 接近 0
- 语义相反 → 接近 -1

工程上通常把向量**归一化**（长度缩放为 1），之后余弦相似度就等价于点积，计算又快又稳。Top-K 检索就是把问题向量和库里的所有向量算一遍相似度，取最近的 K 条——当库很大时，用 [向量数据库](/notes/02-vector-databases) 的索引（HNSW 等）来加速这一步。

## 它和 Token、RAG 是什么关系？

三者的分工可以用一条链路串起来：

```
文本 ──分词──▶ Token序列 ──Embedding模型──▶ 语义向量 ──相似度计算──▶ 检索结果
        [Token篇]              [本篇]                    [RAG篇]
```

- [Token](/notes/03-tokens-and-context) 解决"文字怎么被模型读取、怎么计费"
- **Embedding 解决"意思怎么变成可计算的数学对象"**
- [RAG](/notes/03-rag-basics) 解决"怎么把检索到的知识喂给大模型"

值得强调的一点：**Embedding 模型和大语言模型是两类不同的模型**。前者只负责"理解并压缩语义"，输出向量不输出文字；后者负责生成。RAG 系统里两者协同工作，但选型、部署、计费都是独立的。

## 实践要点

- **选型**：OpenAI `text-embedding-3`、开源 BGE（中文表现好）、Jina Embedding 都是主流选项；看三个指标——效果基准（MTEB 榜单）、维度大小（影响存储）、是否支持中文
- **换模型 = 全量重建**：不同模型的向量空间互不兼容，换 Embedding 模型必须把整个知识库重新向量化——选型时想清楚，别频繁换
- **输入长度有限制**：Embedding 模型也有最大输入 Token 数（通常 512~8K），长文档要先切分，切分策略见 [RAG篇](/notes/03-rag-basics)
- **查询和文档用同一个模型**：检索时问题向量必须和文档向量出自同一模型，否则距离没有意义
- **成本很低**：Embedding 调用价格通常只有生成模型的几十分之一，别在这里过度省钱

## 常见误区

- **"向量越大越准"**：维度高确实容量大，但噪声和存储成本也高；很多 512 维模型效果不输 1536 维
- **"Embedding 能替代全文检索"**：专有名词、型号、代码这类精确匹配场景，关键词检索（BM25）依然更强——所以生产系统常用**混合检索**，两者互补
- **"相似度高 = 答案正确"**：语义相似只说明"话题接近"，不保证内容有用，检索后往往还需要重排序

## 小结

Embedding 的本质是**把语义问题变成几何问题**：文字变成向量后，"意思相不相同"就变成了"距离远不远近"。它是 [向量数据库](/notes/02-vector-databases) 存的东西、[RAG](/notes/03-rag-basics) 检索的依据，也是推荐、去重、聚类等一堆应用的公共底座。

理解了它，你再回头看 RAG 的"检索"环节，会发现核心其实只有一个问题：**怎么让相关的文本在向量空间里靠得更近**——切分、微调 Embedding 模型、重排序，全都是在为这一件事服务。
