# Token与上下文窗口：大模型的记账规则

用大模型 API，两个数字决定一切：**这次请求花了多少 Token**（钱），**还能塞进多少 Token**（上下文窗口）。这两个数字背后是同一套机制——Tokenizer。搞懂它，"为什么费用比预期高""为什么长文对话会忘事"就都有了答案。

## 什么是Token？

大模型并不直接处理文字，而是处理 Token——文本切出来的最小单位。现代模型普遍使用 **BPE（Byte Pair Encoding）** 类算法：

**核心思想**：从字符开始，把语料中高频出现的相邻字符合并成更大的单位，反复迭代。于是：

- 高频英文单词（`the`、`hello`）→ 1 个 Token
- 常见汉字（`的`、`我`）→ 大概率 1 个 Token
- 生僻字、罕见组合 → 可能被拆成多个 Token
- 代码符号、乱码序列 → 可能切得很碎

### 中英文的差异

同样的内容，Token 数量差异不小，而且**换一代词表就会变**：

- 英文：约 **1 Token ≈ 0.75 个单词**（即 1000 Token ≈ 750 词）。常见英文单词大多 1 个 Token
- 中文：新一代词表（如 o200k_base）约 **0.6~0.9 Token / 汉字**，也就是 1 个 Token 能装 1~1.5 个汉字；上一代词表（cl100k_base）要 **1.5~2 Token / 字**。国产模型（Qwen、DeepSeek 等）针对中文优化后还能更低

实践含义：**表达同样内容，中文的 Token 数通常比英文多 20%~60%**（在老一代词表上这个差距会更大）。做中文应用选型时，Tokenizer 的中文效率是实打实的成本差异——同一个模型换词表，成本可能差一倍。

### 亲手感受一下

```python
import tiktoken

enc = tiktoken.encoding_for_model("gpt-4o")   # gpt-4o 使用 o200k_base 词表
print(enc.encode("machine learning"))          # [48082, 7524] → 2 个 Token
print(enc.encode("机器学习"))                   # [96849, 64550] → 2 个 Token

# 老一代词表对比（gpt-3.5-turbo 使用 cl100k_base）
old = tiktoken.encoding_for_model("gpt-3.5-turbo")
print(old.encode("机器学习"))                   # → 5 个 Token，明显更贵

print(len(enc.encode("一段长文本……")))          # 精确计算费用
```

## 上下文窗口：模型的"工作记忆"

上下文窗口 = **一次请求中，模型能"看到"的最大 Token 数**，包含你的系统提示词、历史对话、检索内容、以及模型的回答——**全部加起来**不能超过这个数。

主流模型现状（2026）：从早期 4K，到 128K 成为标配，再到 1M 级别的长上下文模型。但"窗口大"不等于"都塞进去就好"。

### 为什么长对话会"忘事"

两种常见机制导致遗忘：

- **滑动窗口截断**：超过窗口后，最早的对话被直接丢弃——模型"失忆"了
- **注意力稀释**：即使都在窗口内，模型对超长文本中间部分的处理质量也会下降（所谓 "lost in the middle" 现象）——开头和结尾的内容记得最牢

所以"窗口 128K"的实际可用长度要打折扣，**关键信息放开头或结尾、重要历史做摘要压缩**，比无脑堆长度有效得多。

### 费用是怎么算的

API 按 Token 计费，且**输入（Prompt）和输出（Completion）价格不同**，通常输入便宜、输出贵 3~4 倍：

```
费用 = 输入Token × 输入单价 + 输出Token × 输出单价
```

一个容易被忽略的成本：**多轮对话中，历史消息每轮都重新计费**。对话越长，每轮的输入成本越高——第 50 轮的请求，可能带着 3 万 Token 的历史。控制成本的手段：

- 历史对话超过阈值时做**摘要压缩**再拼接
- 系统提示词精简，避免塞入大段无关内容
- RAG 场景控制检索片段数量与长度

### 对应用设计的影响

1. **长文档处理**：文档超过窗口时，要么分段处理再汇总（Map-Reduce），要么走 RAG 只检索相关片段——后者几乎总是更省钱、效果更稳
2. **Agent 场景**：工具调用结果可能很长，及时把旧的观察结果替换为摘要
3. **Max Tokens 设置**：限制输出长度既控制成本，也避免模型跑题写个没完

## 常见误区

- **"Token = 字"**：不对，尤其是中文和代码。估算长度永远用 Tokenizer 实际算，不要按字符数乘系数
- **"窗口大就能塞整个知识库"**：塞得下 ≠ 记得住，长上下文的注意力稀释和成本问题都在
- **"历史对话免费"**：每轮 API 调用都携带全部历史并重新计费——第 N 轮的输入 Token 数正比于 N，N 轮下来总成本是**平方级**增长的

## 小结

Token 是大模型世界的计量单位——**输入输出按它计费，窗口大小按它限制，中英文效率因此差异巨大**。设计 LLM 应用时的三个习惯：用 Tokenizer 精确估算长度、警惕多轮对话的历史膨胀、该用 RAG 时不要硬塞长上下文。
