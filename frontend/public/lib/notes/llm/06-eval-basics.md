# AI应用评测（Eval）入门：别靠感觉优化

AI 应用和传统应用最大的差别是：**输出不确定，对错没有唯一标准答案**。这带来一个致命的工作流问题——你改了切分策略、换了个 Prompt，效果到底变好还是变坏？

- 没有评测：靠感觉、靠三个手测用例、靠老板的主观印象 → 优化方向全靠运气
- 有评测：跑一遍评测集，召回率 +3%、忠实度 -1%，一清二楚

这是"能跑的 Demo"和"能上线的系统"的分界线，也是 [RAG篇](/notes/03-rag-basics) 反复强调"先评估再优化"的原因。

## 评测什么？——把系统拆开看

AI 应用是**多级流水线**，端到端只看最终答案，出了问题都不知道该怪哪一环。正确姿势是分级评测，以 RAG 为例：

| 层级 | 评什么 | 典型指标 |
|------|--------|---------|
| 检索层 | 找没找到相关内容 | 召回率（该找到的找到了多少）、命中率（Top-K 里有没有） |
| 生成层 | 回答质量 | 忠实度（是否忠于检索内容，即幻觉程度）、答案相关性 |
| 端到端 | 用户体验 | 准确率、人工满意度、投诉率 |

**分级评测的核心价值：定位问题**。检索指标高、忠实度低 → 生成侧 Prompt 有问题；召回率低 → 切分或 Embedding 有问题，别急着改 Prompt。

## 第一步：建一个评测集

不要被"评测"两个字吓住，**20~50 条就能支撑前期迭代**：

1. **真实问题优先**：从用户搜索词、客服工单、同事实际提问里收集，比自造的干净数据有价值得多
2. **覆盖难度梯度**：简单事实题、需要综合多条文档的题、故意设计的陷阱题（库里没有答案的题——测系统会不会承认不知道）
3. **标注标准答案**：检索类评测标注"应命中的文档 ID"；生成类标注参考答案或关键要点
4. **badcase 持续沉淀**：线上每个翻车案例，修完就转成一条评测用例——评测集是你系统的"病历本"

```json
{
  "question": "年假可以顺延到明年吗？",
  "expected_docs": ["hr-policy-2026.md#annual-leave"],
  "reference_answer": "不可顺延，当年12月31日清零（特殊情况可申请延长1个月）",
  "type": "single_doc_factual"
}
```

## 第二步：选对评测方法

按成本和可靠度，四档方法从便宜到贵：

| 方法 | 适合评什么 | 成本 | 注意点 |
|------|-----------|------|--------|
| 规则断言 | 格式、必含要素、长度 | 极低 | 只能查"有没有"，查不了"对不对" |
| 相似度 | 答案与参考答案的接近程度 | 低 | 用 [Embedding](/notes/05-embeddings-and-semantic-search) 余弦相似度，粗筛好用 |
| LLM-as-Judge | 忠实度、相关性等无标准答案的维度 | 中 | 让强模型当裁判，按评分细则打分 |
| 人工评审 | 上线前的最终把关 | 高 | 抽样即可，重点看 LLM 裁判拿不准的部分 |

**LLM-as-Judge 是当前性价比最高的主力方案**，示例 Prompt 骨架：

```
你是严格的质检员。根据【参考资料】判断【回答】是否完全有依据。
完全有依据 → 1 分；部分编造 → 0.5 分；与资料矛盾 → 0 分。
只输出分数和理由。

【参考资料】{retrieved_docs}
【回答】{answer}
```

三个防坑要点：**给评分细则**（什么叫"有依据"要写清楚）、**换裁判模型验证**（防止裁判自己的偏好污染结果）、**结论只信相对值**（A 方案 0.86 分 vs B 方案 0.79 分有意义，绝对分数没有）。

## 第三步：让评测跑进日常流程

评测最大的价值不在"测一次"，而在**回归**：

- 每次改 Prompt、换模型、调切分参数 → 先跑一遍评测集，指标不达标不合入
- 把评测脚本接进 CI，和单元测试同等地位
- 指标报表按周看趋势：模型 API 静默升级、知识库内容变化，都会在趋势里现形

```
改切分策略 256 → 512 tokens
  召回率:  78% → 89%   ✅
  忠实度:  92% → 91%   ⚠️ 轻微下降，可接受
结论：合入
```

## 常见坑

- **评测集被"过拟合"**：反复对着同一批用例调优，会失去泛化性——留 20% 作盲测集，只在里程碑时跑
- **只测正常用例**：陷阱题（无答案、超纲、诱导编造）往往比正常题更能暴露问题
- **指标当目标**：召回率上去了但检索回来的都是废话，说明该看的是排序质量，别单指标最优
- **一上来就追求全自动**：先用表格手工记录 20 条的得分也能支撑决策，工具（RAGAS、TruLens、promptfoo）是后来才需要的

## 小结

评测的完整闭环：**建评测集（真实问题 + badcase 沉淀）→ 分级评测（检索/生成/端到端）→ LLM-as-Judge 主力、人工把关 → 接入日常迭代做回归**。

它的意义远不止"量化效果"——评测集本质上是你系统行为的**可执行规格说明**。有了它，[可观测与成本治理](/notes/07-observability-and-cost) 的线上数据才能回流成新的评测用例，[模型微调](/notes/05-model-finetuning) 之前的"要不要微调"才有依据可谈。
