# 推理优化：量化与KV Cache在做什么

当你的 AI 应用从"能跑"走向"规模化"，推理侧的三个指标就会顶到眼前：**延迟**（用户等不了）、**吞吐**（并发扛不住）、**显存**（卡太贵）。这篇讲清楚这些指标背后的瓶颈原理，以及两个最重要的优化手段——KV Cache 和量化——到底在做什么。

前提认知：[Transformer架构](/notes/01-transformer-architecture) 的自回归生成方式决定了推理的两个阶段——**Prefill**（一次性处理整个 Prompt，计算密集）和 **Decode**（一个 Token 一个 Token 蹦出来，访存密集）。所有优化手段都是在针对这两个阶段做文章。

## KV Cache：用空间换时间的缓存

### 问题：重复计算

生成第 N 个 Token 时，注意力机制要用它和**前面所有 Token** 做交互。如果每生成一个 Token 就把前文重新算一遍，生成 1000 个 Token 的成本是平方级的——根本不可行。

### 解法：把历史算过的缓存下来

注意力计算需要两样中间产物：Key 和 Value 矩阵。它们对"历史 Token"来说是**不变的**——第 3 个 Token 的 KV，无论后面生成多少内容，它永远是那个值。所以：

```
生成每个新 Token 时：
  只计算新 Token 自己的 K、V，追加进缓存
  注意力只做"新 Token 查缓存"这一步
```

一次 Prefill + N 次"查缓存"的 Decode，把平方级降成了线性。**这就是所有现代推理引擎的地基**，[vLLM](/notes/03-local-llm) 的 PagedAttention 也是在解决"这个缓存怎么管得更省"的问题。

### KV Cache 的显存账

天下没有免费的缓存。KV Cache 大小有个简单的估算公式：

```
KV Cache 显存 ≈ 2 × 层数 × KV头数 × 头维度 × 序列长度 × 批大小 × 每元素字节数
```

代入一个 7B 模型（32 层、FP16）粗算：**单条 4K 上下文的请求就要吃掉约 0.5~1 GB 显存**。这意味着：

- 显存的大头往往不是模型参数，而是**并发请求的 KV Cache**——这直接限制了批大小，也就是限制了吞吐
- **长上下文是显存杀手**：上下文翻倍，KV Cache 翻倍，可并发的请求数减半
- 由此衍生出两个常见优化：**GQA/MQA**（多个 Query 头共享一组 KV 头，直接砍缓存体积，主流模型已标配）和 **前缀缓存**（相同系统 Prompt 的 KV 只算一次，多会话共享）

## 量化：把数字变"粗"来省显存

### 直觉：降低数字的精度

模型参数默认用 FP16 存储（每个数 2 字节）。量化就是用更少的比特表示同一个数：INT8（1 字节）显存减半，INT4（0.5 字节）只剩四分之一。一个 7B 模型的权重：

| 精度 | 权重显存 | 说明 |
|------|---------|------|
| FP16 | ~14 GB | 原始精度 |
| INT8 | ~7 GB | 几乎无感损失 |
| INT4 | ~3.5 GB | 轻微损失，消费级显卡的救星 |

这就是为什么 [本地部署篇](/notes/03-local-llm) 里 7B 模型的 Q4 版本能在 8GB 显卡上跑——**"Q4"指的就是 4 比特量化**。

### 主流方案与取舍

- **GGUF（llama.cpp 系）**：单机/端侧首选，Q4_K_M 这类混合精度格式在大小和质量间平衡得很好
- **AWQ / GPTQ**：面向 GPU 推理服务，INT4 下质量保持较好，vLLM 原生支持
- **FP8**：新一代硬件（H 系列）的甜点精度，接近无损，服务端量化趋势

关键认知：**量化牺牲的是"离群值以外的精度"**。模型权重分布里有极少数很大的"离群值"承载了大部分信息，现代量化方法的核心就是把这些值保护起来（单独高精度存储或缩放），其余的放心压低。所以 Q4 的损失远比直觉小，但也**不是零**——量化后的模型必须过一遍 [评测集](/notes/06-eval-basics) 再上线，这一步不能省。

## 批处理与投机解码

### Continuous Batching：吞吐的倍增器

传统静态批处理要等一批请求全部生成完才能进下一批——长短请求互相拖累。**Continuous Batching**（由 Orca 系统首次提出，vLLM 将其做成工程标准实现）：每个 Decode 步骤后动态地让完成的请求退出、新请求插入，GPU 几乎没有空转，**吞吐轻松提升数倍到数十倍**。

### 投机解码：小模型替大模型"打草稿"

一个反直觉的技巧：**用小模型快速猜出后续几个 Token，大模型一次并行验证**。验证比生成便宜（Prefill 是并行的），猜对了白赚，猜错了退回重来。因为验证正确率很高（简单内容小模型也能猜对），端到端延迟可降 2~3 倍，**且输出分布与大模型完全一致**——是"无损加速"。

## 怎么选？——组合决策

| 你的处境 | 优先做什么 |
|---------|-----------|
| 延迟高、用户抱怨慢 | TTFT 分段定位 → Prefill 慢上前缀缓存；Decode 慢考虑投机解码 |
| 并发上不去、GPU 便宜 | Continuous Batching（换 vLLM）+ 检查 KV Cache 显存占比 |
| 显存不够、想上长上下文 | KV Cache 侧：GQA 模型；权重侧：AWQ/GPTQ INT4；必要时上下文裁剪 |
| 预算有限先省钱 | 量化前先做 [成本核算](/notes/07-observability-and-cost)——很多"性能问题"其实是"该路由到小模型的问题" |

原则就一条：**先测量，再优化**。不知道瓶颈在 Prefill 还是 Decode、在权重还是 KV Cache，一切优化都是赌博。

## 小结

推理优化的三块拼图：**KV Cache 把生成从平方降到线性、但显存账决定并发上限**；**量化压权重换显存，离群值保护让它损失可控，但必须回归评测**；**Continuous Batching 和投机解码分别榨吞吐和降延迟**。

这些是模型服务侧的功夫。对大多数应用工程师来说，不必手写这些技术，但**必须理解它们的代价与收益**——这样才能在选模型、选部署方案、算成本时，和基础设施同学说同一种语言。
