# LLM应用可观测与成本治理

AI 应用上线只是开始。和传统服务相比，它多了两根敏感的神经：**输出不确定**（质量会漂移）和**按 Token 计费**（成本随业务线性增长）。可观测与成本治理就是盯住这两根神经的眼睛——[评测](/notes/06-eval-basics) 告诉你"效果好不好"，本篇告诉你"线上到底发生了什么、钱花在了哪"。

## 记录什么？——五要素日志

每次模型调用至少留下这五样东西，缺一不可：

| 要素 | 内容 | 用途 |
|------|------|------|
| 输入输出 | Prompt（含版本号）、检索内容、完整回答 | 排查 badcase、复现问题 |
| Token 消耗 | 输入/输出 Token 数、命中的上下文长度 | 成本核算的第一手数据 |
| 延迟 | 总耗时、**首 Token 时间（TTFT）** | 流式应用的关键体感指标 |
| 版本指纹 | 模型版本、Prompt 版本、切分/检索参数 | 出问题才知道"谁变了" |
| 业务标签 | 用户/租户 ID、业务线、功能场景 | 成本与质量的归因维度 |

**Prompt 版本号最容易被忽略，也最致命**：模型 API 会静默升级，你改了 Prompt 没记录，回头分析质量波动时两头都说不清。

## 延迟：看 P99，更要看首 Token

- **P99 而非平均值**：长尾请求（超长上下文、限流重试）才是用户流失的元凶，平均数会把它抹平
- **TTFT（Time To First Token）**：流式应用用户感知的是"多久开始出字"，不是"多久出完"。优化它比优化总时长收益更大
- **分段计时**：检索耗时和生成耗时分开记——RAG 慢，先分清是 [向量检索](/notes/02-vector-databases) 慢还是模型慢

## 工具链：不必从零造轮子

- **LLM 专用可观测平台**：Langfuse（开源可自部署）、LangSmith——开箱即得调用树、Token 统计、Prompt 版本管理、评测数据回流
- **传统 APM**：模型调用当成普通外部依赖，用你现有的 SkyWalking/Jaeger 打 trace
- **自建兜底**：上面都不想要，就在应用层把五要素日志打进现有日志系统，用 SQL 也能做出 80% 的分析

Java 侧（Spring AI）可以把每次调用包成 Micrometer 指标 + 结构化日志，直接接入 [你现有的监控体系](/notes/04-java-ai-transition)——观测 AI 服务的基建和观测普通服务没有本质区别。

## 成本治理：从"账单惊吓"到"按线核算"

### 第一步：把成本归因到业务线

原始账单只有"这个 API Key 花了多少"，没法定价、没法优化。靠日志里的业务标签做**分摊核算**：

```
成本 = Σ（每次调用的输入Token × 输入单价 + 输出Token × 输出单价）
      按 业务线 × 功能场景 × 模型 三个维度聚合
```

这一步做完，通常会立刻发现：某个内部测试功能烧掉了 40% 的预算。

### 第二步：识别治理点

按性价比排序的常见优化手段：

- **输出截断**：输出 Token 单价通常是输入的 3~4 倍，管住"说太多"收益最大——限制 max_tokens、要求简洁作答
- **语义缓存**：高频重复问题（"怎么改密码"）命中缓存直接返回，热门场景能省 30%+；用 [Embedding](/notes/05-embeddings-and-semantic-search) 相似度判断"是不是同一个问题"
- **模型路由**：简单任务（分类、抽取）路由到小模型，复杂任务才走旗舰模型——分级计费立竿见影
- **Prompt 瘦身**：系统 Prompt、few-shot 示例、检索内容都会乘以请求量；把不变的部分挪到缓存命中的前缀里
- **上下文管理**：多轮对话历史无限堆积是成本黑洞，做摘要压缩或滑动窗口，机制见 [Token与上下文窗口](/notes/03-tokens-and-context)

### 第三步：设预算与告警

- 按业务线设月度预算，超 80% 告警（和监控告警同一个体系）
- 区分**必要成本**和**泄漏**：泄漏指重试风暴、调试流量打到生产模型、缓存失效导致的重复调用

## 质量与成本的联动

可观测和成本不能两张皮。三个联动机制：

1. **badcase 回流**：可观测日志里的翻车样本，沉淀进 [评测集](/notes/06-eval-basics)，形成质量闭环
2. **成本异常 = 质量异常的线索**：Token 消耗突增，往往是模型输出失控（开始复读）的信号
3. **降级预案**：模型故障或预算耗尽时，降级到小模型/规则引擎，[评测集](/notes/06-eval-basics) 里提前备好降级档位的质量数据

## 小结

可观测与成本治理的本质：**给"不确定的系统"装上仪表盘和油表**。五要素日志是地基，P99 + TTFT 是体感指标，按业务线核算是成本抓手，缓存/路由/瘦身是治理三板斧。

这些能力建好后，你的 AI 应用才真正拥有了传统服务的运维水位——这也是 [Java 工程师做 AI](/notes/04-java-ai-transition) 最能发挥存量优势的地方。下一块硬骨头在性能侧：模型推理本身怎么提速省钱，见 [推理优化：量化与KV Cache](/notes/08-inference-optimization)。
